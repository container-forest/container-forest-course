# Ретроспектива: SignalR

- Пакет: `@microsoft/signalr` (JS-клієнт у панелі). Серверна частина — частина ASP.NET Core і в облік лаби 3 не йде; оцінюється клієнт: окремий пакет із реальними альтернативами.

Кожен учасник, що працював із бібліотекою, пише свій розділ за питаннями з умови лаби 3.

## Петренко Б. О.

### Які задачі розв'язує бібліотека

- Live-оновлення панелі: ЦА повідомляє через `/hubs/live`, що змінилися середовища, контейнери, стеки чи деплої, і панель одразу перечитує ці дані (`HubProvider` інвалідовує запити TanStack Query). Екрани деплоїв більше не опитують ЦА кожні 2 с, поки з'єднання живе.
- Стан з'єднання для користувача: «Наживо» / «Перепідключення…» в шапці, зокрема поки ЦА оновлюється (вимога з розділу «Самокерування» архітектури).

### Чому саме ця бібліотека

Альтернативи: голий `WebSocket` браузера, Server-Sent Events (`EventSource`), Socket.IO. Сервер на ASP.NET Core, а SignalR — його вбудований механізм: групи, автентифікація тією самою cookie, вибір транспорту (WebSocket, SSE, long polling) і повторне з'єднання. Для голого WebSocket чи SSE повторне з'єднання, протокол повідомлень і групи довелося б писати самим; Socket.IO потребує власного сервера на Node.

### Документація

Документація Microsoft Learn детальна й з прикладами для обох боків; добре описані автентифікація, групи й `withAutomaticReconnect`. Менш очевидні речі: чим `HttpContext` у хабі відрізняється від звичайного запиту і що автоматичне повторне з'єднання не покриває перший старт — це з'ясовувалося тестами.

### Проблеми та як їх розв'язали

1. **Порожній `IHttpContextAccessor` у хабі.** Сервіси ЦА беруть користувача через `ICurrentUser`, а той — з `IHttpContextAccessor`. У виклику хабу його `HttpContext` порожній (інтеграційний тест з long polling одразу закривав з'єднання з `UnauthenticatedException`; причину показало `EnableDetailedErrors` у Development). Хаб передає `Context.User` у `ClaimsCurrentUser.Use` на час виклику.
2. **Перший старт.** `withAutomaticReconnect` діє лише після того, як з'єднання вже було; якщо ЦА недоступний під час відкриття панелі, `start()` просто падає. `HubProvider` повторює старт сам, з тим самим backoff, а на 401/403 зупиняється.
3. **Пропущені події.** Поки з'єднання немає (оновлення ЦА), події губляться. Після повторного з'єднання панель перечитує всі запити.
4. **Права.** Події свідомо несуть лише id: що показати, вирішує API при перечитуванні. Щоб id чужих середовищ узагалі не доходили, з'єднання входить у групи лише видимих середовищ і перепідписується, коли змінюються ролі.
5. **Тести.** Тестовий сервер не дає клієнту справжнього WebSocket; інтеграційні тести ходять через long polling (`HttpMessageHandlerFactory` тестового сервера), а WebSocket перевірено вручну через проксі Vite і в браузері: стек, створений через API, з'являється на екрані без перезавантаження, а перезапуск ЦА показується як «Перепідключення…» і минає сам.

### Плюси й мінуси

Плюси:

- типізований хаб на сервері (`Hub<ILiveClient>`) і кілька рядків клієнта;
- повторне з'єднання, групи й автентифікація cookie без власного коду;
- той самий клієнт працює через Caddy і через проксі Vite без налаштувань.

Мінуси:

- типи подій у TypeScript пишуться вручну, OpenAPI їх не описує;
- пакет додає до бандла помітний обсяг (клієнт підтримує всі транспорти й протоколи);
- поведінку `HttpContext` у хабі довелося з'ясовувати на практиці.

### Що змінили б

Так само: лише id у подіях і перечитування через API, публікація з одного місця (збереження в БД), а не з кожного сервісу. Інакше: одразу писати інтеграційний тест хабу, а не покладатися на те, що автентифікація «така сама, як для REST».
