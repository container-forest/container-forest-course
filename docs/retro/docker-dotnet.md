# Ретроспектива: Docker.DotNet

- Пакет: `Docker.DotNet.Enhanced` 4.3.3 (форк Docker.DotNet від Testcontainers)

Кожен учасник, що працював із бібліотекою, пише свій розділ за питаннями з умови лаби 3.

## Бояр В. О.

### Які задачі розв'язує бібліотека

- Агент звертається до Docker Engine на своєму хості: версія Docker для `Hello`, список контейнерів, запуск, зупинка й перезапуск контейнера (`src/Agent/Docker/DockerDotNetGateway.cs`).
- Бібліотека сама знаходить endpoint Docker так само, як docker CLI: `DOCKER_HOST`, потім поточний Docker-контекст, потім типовий сокет (`/var/run/docker.sock` на Linux, named pipe на Windows). Шлях до сокета в агенті не захардкоджено.
- Читання логів контейнера для панелі (`ReadContainerLogsAsync`): `Containers.GetContainerLogsAsync` з часом кожного рядка, розбір потоку на stdout і stderr — `src/Agent/Docker/ContainerLogParser.cs`.
- Далі: події контейнерів (live-оновлення панелі) і живий потік логів (`follow`).

### Чому саме ця бібліотека

Альтернативи: викликати `docker` CLI і розбирати його вивід або писати HTTP-запити до Docker Engine API вручну. Docker.DotNet дає типізовані моделі API й типізовані винятки. `docker compose` агент однаково викликатиме через CLI (там бібліотека не допоможе), але прості операції з контейнерами зручніше робити через API.

Оригінальний пакет `Docker.DotNet` (3.125.15) оновлюється рідко. Форк `Docker.DotNet.Enhanced` підтримує Testcontainers: регулярні релізи (останній — червень 2026), збірка під .NET 10, Docker API v29. Обрали форк.

### Документація

Окремої документації у форку майже немає, і це головна незручність. API я з'ясовував з XML-коментарів пакета й перевіряв невеликою програмою (`dotnet run probe.cs` з директивою `#:package`), а поведінку Docker (304 для «вже запущений», формат тіла помилки) — у довіднику Docker Engine API, бо бібліотека лише повторює його модель. Приклади з інтернету написані для оригінального пакета, де клієнт створюється через `DockerClientConfiguration`; у версії 4.x форку його замінив `DockerClientBuilder`, тож вони не компілюються й можуть заплутати.

### Проблеми та як їх розв'язали

1. **Інший API створення клієнта.** Приклади для `Docker.DotNet` (`new DockerClientConfiguration().CreateClient()`) не компілюються з форком 4.x. Правильно — `new DockerClientBuilder().Build()`.
2. **Таймаут клієнта 100 с.** ЦА дозволяє час коректної зупинки контейнера до 5 хв, а Docker відповідає на `stop` лише після зупинки. Глобальний таймаут вимкнено (`WithTimeout(Timeout.InfiniteTimeSpan)`), а кожен виклик отримує власний бюджет: 30 с для швидких запитів, 30 с + час зупинки для stop/restart. Коли бюджет вичерпано, повертається `ERROR_CODE_TIMEOUT`.
3. **Як виглядає «Docker недоступний».** На Windows з вимкненим Docker Desktop підключення до named pipe чекає 10 с і кидає `TimeoutException`; на Linux це `HttpRequestException` / `SocketException`. Усі такі винятки агент перетворює на `ERROR_CODE_DOCKER_UNAVAILABLE`, і панель показує 502 з текстом «Docker is not reachable on this host.».
4. **«Вже запущений» і «вже зупинений».** Docker відповідає 304, а бібліотека повертає `false` зі `StartContainerAsync` / `StopContainerAsync`. Для агента це успіх, бо бажаний стан уже досягнуто.
5. **Помилки Docker для користувача.** `DockerApiException.Message` містить службовий текст разом із JSON-тілом. Агент бере з `ResponseBody` лише поле `message` (наприклад, «cannot restart container…») і передає в панель тільки його.
6. **Id контейнера стає частиною шляху запиту.** Щоб рядок з `/` чи `..` не звернувся до іншого endpoint'а Docker API, id перевіряється регулярним виразом `^[a-zA-Z0-9][a-zA-Z0-9_.-]*\z` ще до виклику бібліотеки.
7. **Час створення контейнера.** `ContainerListResponse.Created` — це `DateTime`, тож для unix-мілісекунд у протоколі `Kind` явно приводиться до UTC.
8. **Контейнер із TTY.** Логи такого контейнера — один сирий потік, без заголовків stdout/stderr. В оригінальному пакеті `GetContainerLogsAsync` приймав параметр `tty`, у форку його немає, і з XML-коментарів не видно, як бібліотека це вирішує. Декомпіляція (`ilspycmd`) показала, що метод сам робить `InspectContainerAsync` і бере `Config.Tty`, тож `MultiplexedStream.ReadOutputAsync` правильно повертає `StandardOut` для TTY-контейнера. Ціна — зайвий запит, а «контейнера немає» приходить уже з inspect.
9. **Логи — це байти, а не рядки.** `ReadOutputAsync` віддає шматки буфера, які можуть рвати рядок і навіть символ UTF-8 посередині, а шматки stdout і stderr чергуються. Агент збирає рядки окремо для кожного потоку (`ContainerLogParser`), декодує UTF-8 із заміною невалідних байтів і обрізає рядок до 16 КБ, щоб пачка `LogBatch` вкладалася в ліміт gRPC. Перевантаження з `IProgress<string>` віддає готові рядки, але губить, з якого вони потоку.
10. **Час рядка.** З `Timestamps = true` Docker пише час із наносекундами (`2026-10-02T12:00:00.123456789Z`), а `DateTimeOffset` розбирає щонайбільше 7 знаків після коми: зайві цифри агент відкидає. `Since` у бібліотеці — рядок, і Docker приймає `секунди.наносекунди`, тож межа зберігає мілісекунди.
11. **Довгі й незавершені рядки.** Docker сам ділить рядок довший за 16 КБ на часткові записи, кожен зі своїм часом, і `tail` рахує саме записи. Рядок без `
` у кінці з'являється в логах лише тоді, коли контейнер допише його або завершиться. Обидва випадки — поведінка Docker, а не агента; перевірено порівнянням із `docker logs -t`.

### Плюси й мінуси

Плюси:

- типізовані моделі й винятки (`DockerContainerNotFoundException`, `DockerApiException`) замість розбору тексту docker CLI;
- endpoint визначається так само, як у docker CLI, і на Linux, і на Windows, тож агент не має захардкодженого шляху до сокета;
- форк активно підтримується й збирається під .NET 10.

Мінуси:

- документації для форку майже немає, а API змінюється між мажорними версіями;
- глобальний таймаут 100 с за замовчуванням не підходить для довгих зупинок, бюджет часу довелося задавати кожному виклику;
- різні винятки для «Docker недоступний» на Linux і Windows;
- `docker compose` бібліотека не покриває, для стеків однаково потрібен CLI;
- логи бібліотека віддає сирими байтами: розбір рядків, часу й кодування довелося писати самим.

### Що змінили б

Так само: форк замість закинутого оригіналу і власний бюджет часу на кожен виклик. Інакше: на самому початку зібрати маленьку програму-зонд для кожного виклику, який знадобиться (список, start/stop, помилки, недоступний Docker на обох ОС), і зберегти її в репозиторії поруч із тестами: вона й була найкращою документацією, а так її можна було б повторно запустити після оновлення пакета.
