# Ретроспектива: Entity Framework Core

- Пакети: `Microsoft.EntityFrameworkCore.Sqlite`, `Microsoft.EntityFrameworkCore.Design`, інструмент `dotnet-ef`

Кожен учасник, що працював із бібліотекою, пише свій розділ за питаннями з умови лаби 3.

## Петренко Б. О.

### Які задачі розв'язує бібліотека

- Зберігання доменної моделі ЦА (середовища, репозиторії, стеки, деплої, користувачі, ролі) в SQLite без окремих persistence-моделей: EF мапить доменні класи з приватними сеттерами напряму.
- Міграції схеми: перша міграція `InitialCreate`, автоматичне застосування при старті ЦА.
- Конвертери значень: типізовані ID (`EnvironmentId` тощо) і value objects (`StackName`, `BranchName`, `CommitSha`) зберігаються як прості колонки.
- Успадкування: `EnvironmentRoleAssignment` і `StackRoleAssignment` в одній таблиці (TPH, колонка-дискримінатор `Scope`).

### Чому саме ця бібліотека

Альтернативи: Dapper (ручний SQL і мапінг), linq2db, NHibernate. Обрали EF Core, бо:

- міграції схеми з коробки, без окремого інструмента;
- доменні сутності можна зберігати як є: приватні сеттери, конструктори для EF, конвертери для value objects;
- LINQ-запити замість SQL-рядків, типізовані й перевірені компілятором;
- у майбутньому можна перейти з SQLite на PostgreSQL зміною провайдера (хоча міграції тоді доведеться вести окремо).

### Документація

Документація EF Core — найповніша з усіх бібліотек, які я використовував у проєкті. Кожна тема (конвертери значень, успадкування, міграції) має окрему сторінку з прикладами, а обмеження SQLite зібрані на одній сторінці провайдера: проблему з `DateTimeOffset` я знайшов там раніше, ніж вона проявилась. Бракувало опису того, що лежить на межі EF і решти платформи. Що генератор OpenAPI під час збірки запускає hosted-сервіси (і разом із ними міграції), з'ясувалося, лише коли `dotnet build` створив базу. Що дерева виразів не допускають виклику `static abstract` члена, підказала помилка компіляції, а не документація.

### Проблеми та як їх розв'язали

1. **SQLite не має типу `DateTimeOffset`.** Збережені як текст, дати не можна порівнювати й сортувати в запитах. Усі `DateTimeOffset` зберігаються як `long` через `DateTimeOffsetToBinaryConverter`, заданий один раз конвенцією в `ConfigureConventions`.
2. **Узагальнений конвертер ID.** Конвертер мав викликати `TId.From(guid)` (статичний абстрактний член інтерфейсу), але дерева виразів EF такого виклику не допускають. Виклик загорнуто у звичайний статичний метод `Create`.
3. **Міграції запускались під час збірки.** Генератор OpenAPI-документа (`GetDocument.Insider`) стартує хост ЦА разом із hosted-сервісами, тож `dotnet build` створював базу. У цьому режимі реєстрацію `DatabaseMigrator` вимкнено.
4. **Та сама властивість у двох підкласах TPH.** І роль на середовищі, і роль на стеку мають `EnvironmentId`. Обидві мапляться в одну колонку через `HasColumnName`, а унікальний індекс «користувач + середовище» відфільтровано за дискримінатором.
5. **`DbContext` у довгому gRPC-виклику.** З'єднання агента живе годинами; один `DbContext` на весь виклик тримав би застарілі сутності. Кожна операція з БД виконується в окремому DI-scope.
6. **Назви без урахування регістру.** Унікальність назв середовищ, репозиторіїв і користувачів — через колацію `NOCASE`, а не нормалізацію рядків у коді.
7. **Інструмент міграцій.** `dotnet-ef` поставлено локальним інструментом (`dotnet-tools.json`), щоб у всіх була однакова версія; `IDesignTimeDbContextFactory` дає створювати міграції без запуску ЦА.
8. **Лог деплою як частина сутності.** Рядки логу — owned-колекція `Deployment` (`OwnsMany`, окрема таблиця `DeploymentLogLines`) з ключем «деплой + номер рядка». EF не гарантує порядок елементів колекції при завантаженні, тому кожен рядок має `Sequence`, а `Deployment.Log` сортує за ним. Історія деплоїв читається проєкцією в `DeploymentSummary`, щоб не тягнути тисячі рядків логу для кожного запису.

### Плюси й мінуси

Плюси:

- доменні класи зберігаються як є, з приватними сеттерами й конструктором для EF, тож окремих persistence-моделей і мапінгу між ними немає;
- те, що в домені виражено типами (`StackName`, типізовані ID), один раз описується конвертером або конвенцією й далі працює в усіх запитах;
- міграції з коробки, а `IDesignTimeDbContextFactory` дає створювати їх без запуску ЦА;
- LINQ-запити перевіряє компілятор, а проєкції (`DeploymentSummary`) не тягнуть зайвих даних.

Мінуси:

- обмеження провайдера видно лише під час виконання: запит із сортуванням за `DateTimeOffset` компілюється, а падає на SQLite;
- конфігурація розростається: 12 класів `IEntityTypeConfiguration` для двох десятків сутностей;
- типізовані ID з конвертером не всюди проходять: зовнішній ключ з таблиці ASP.NET Identity на `Users` налаштувати не вдалося (див. розділ Денисенко Л. В.);
- за замовчуванням у лог потрапляє кожен SQL-запит, рівень для `Database.Command` довелося знизити до Warning.

### Що змінили б

Так само: мапити домен напряму, без окремих моделей, і з першого дня задати конвенції для дат і ID в `ConfigureConventions`. Інакше: на кожен новий запит із фільтром чи сортуванням писати інтеграційний тест на справжній SQLite, а не покладатися на компіляцію, бо саме так проявляються обмеження провайдера. Якщо проєкт житиме після курсу, перейти на PostgreSQL раніше: кожна нова міграція для SQLite — це ще одна міграція, яку доведеться переписувати.

## Бояр В. О.

### Які задачі розв'язує бібліотека

- Зберігання кредів container registry на середовищі (`RegistryCredential`): таблиця `RegistryCredentials` з каскадним видаленням разом із середовищем і унікальним індексом «середовище + адреса registry», щоб повторне збереження для того самого registry замінювало логін, а не дублювало його.
- Пароль зберігається лише зашифрованим (`ProtectedPassword`, ADR-0003); EF бачить звичайний рядок, а шифрує й розшифровує сервіс через `ISecretProtector`.
- Міграція `RegistryCredentials`.

### Чому саме ця бібліотека

EF Core уже використовується в ЦА для всієї доменної моделі (див. розділ Петренка Б. О.); нова сутність лише додає клас конфігурації й міграцію.

### Документація

Для такої задачі вистачило сторінок про зовнішні ключі й індекси та готових конфігурацій інших сутностей у проєкті як зразка.

### Проблеми та як їх розв'язали

- **Шифрування поза EF.** Конвертер значень міг би шифрувати пароль прозоро, але тоді розшифрування відбувалося б під час кожного завантаження сутності, а помилка ключа (втрачений key ring) виникала б посеред запиту. Пароль зберігається вже зашифрованим, а розшифровується лише в кроці деплою, що збирає креди для агента; втрачений ключ дає зрозумілу помилку `SecretUnreadableException`.

### Плюси й мінуси

Плюс: нова таблиця з обмеженнями — це один клас на два десятки рядків і згенерована міграція. Мінус: міграції з паралельних гілок конфліктують у `AggregatorDbContextModelSnapshot.cs`, і після мерджу міграцію доводиться перегенеровувати.

### Що змінили б

Перед створенням міграції підтягувати свіжий `main`, щоб не перегенеровувати її після мерджу чужих міграцій.

### Використані ресурси

- Зв'язки й зовнішні ключі: https://learn.microsoft.com/ef/core/modeling/relationships
- Індекси: https://learn.microsoft.com/ef/core/modeling/indexes

## Денисенко Л. В.

### Які задачі розв'язує бібліотека

- Таблиці облікових записів ASP.NET Identity (`AspNetUsers`, `AspNetUserClaims`, `AspNetUserLogins`, `AspNetUserTokens`) у тій самій базі й тому самому `AggregatorDbContext`: він успадковує `IdentityUserContext<AccountUser, Guid>`, без таблиць ролей (ролі в проєкті — власні, доменні).
- Міграція `Accounts`.

### Чому саме ця бібліотека

ASP.NET Identity зберігає облікові записи через EF Core (`Microsoft.AspNetCore.Identity.EntityFrameworkCore`), а ЦА вже працює з EF Core: окрема база чи окремий контекст для облікових записів не дали б нічого, крім двох транзакцій там, де потрібна одна.

### Документація

Сторінка про налаштування моделі Identity пояснює, які базові контексти є (`IdentityUserContext` без ролей, `IdentityDbContext` з ролями) і як змінити тип ключа. Про конфлікт з наявною властивістю `Users` там не сказано.

### Проблеми та як їх розв'язали

- **Дві властивості `Users`.** `IdentityUserContext` має власну `Users`, а в `AggregatorDbContext` вже була `DbSet<User> Users` для доменних користувачів. Приховування члена — попередження, а в CI — помилка збірки. Нашу властивість прибрали: таблицю доменних користувачів задає `ToTable("Users")`, а запити йдуть через `Set<User>()` у репозиторії.
- **Зовнішній ключ на доменного користувача.** `AspNetUsers.Id` має тип `Guid`, а `Users.Id` — `UserId` з конвертером; EF не з'єднує ці типи у зовнішній ключ. Цілісність тримає код: обліковий запис і доменний користувач створюються в одному `SaveChanges`.

### Плюси й мінуси

Плюс: таблиці Identity з'явилися однією зміною базового класу й однією міграцією. Мінус: базовий клас бібліотеки приносить у наш контекст свої члени й назви таблиць, і з ними треба уживатися.

### Що змінили б

Перевірити назви членів базового класу перед тим, як його успадковувати, і одразу вирішити, як зв'язати типізований id з ключем Identity.
