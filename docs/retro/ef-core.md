# Ретроспектива: Entity Framework Core

- Пакети: `Microsoft.EntityFrameworkCore.Sqlite`, `Microsoft.EntityFrameworkCore.Design`, інструмент `dotnet-ef`
- ⚠️ Пакет Microsoft: чи зараховується він у лабу 3, треба підтвердити у викладача.

Кожен учасник, що працював із бібліотекою, пише свій розділ за питаннями з умови лаби 3.

## Петренко Б. О.

Статус: **чернетка.** Факти про задачі й проблеми заповнено; розділи з оцінками — дописати автору.

### Які задачі розв'язує бібліотека

- Зберігання доменної моделі ЦА (середовища, репозиторії, стеки, деплої, користувачі, ролі) в SQLite без окремих persistence-моделей: EF мапить доменні класи з приватними сеттерами напряму.
- Міграції схеми: перша міграція `InitialCreate`, автоматичне застосування при старті ЦА.
- Конвертери значень: типізовані ID (`EnvironmentId` тощо) і value objects (`StackName`, `BranchName`, `CommitSha`) зберігаються як прості колонки.
- Успадкування: `EnvironmentRoleAssignment` і `StackRoleAssignment` в одній таблиці (TPH, колонка-дискримінатор `Scope`).

### Чому саме ця бібліотека

Альтернативи: Dapper (ручний SQL і мапінг), linq2db, NHibernate. Обрали EF Core, бо:

- міграції схеми з коробки, без окремого інструмента;
- доменні сутності можна зберігати як є: приватні сеттери, конструктори для EF, конвертери для value objects;
- LINQ-запити замість SQL-рядків, типізовані й перевірені компілятором;
- у майбутньому можна перейти з SQLite на PostgreSQL зміною провайдера (хоча міграції тоді доведеться вести окремо).

### Документація

_Дописати автору._

Факти: обмеження SQLite (зокрема з `DateTimeOffset`) описані на окремій сторінці документації провайдера; про те, що генератор OpenAPI під час збірки запускає hosted-сервіси, довелося дізнаватися експериментом.

### Проблеми та як їх розв'язали

1. **SQLite не має типу `DateTimeOffset`.** Збережені як текст, дати не можна порівнювати й сортувати в запитах. Усі `DateTimeOffset` зберігаються як `long` через `DateTimeOffsetToBinaryConverter`, заданий один раз конвенцією в `ConfigureConventions`.
2. **Узагальнений конвертер ID.** Конвертер мав викликати `TId.From(guid)` (статичний абстрактний член інтерфейсу), але дерева виразів EF такого виклику не допускають. Виклик загорнуто у звичайний статичний метод `Create`.
3. **Міграції запускались під час збірки.** Генератор OpenAPI-документа (`GetDocument.Insider`) стартує хост ЦА разом із hosted-сервісами, тож `dotnet build` створював базу. У цьому режимі реєстрацію `DatabaseMigrator` вимкнено.
4. **Та сама властивість у двох підкласах TPH.** І роль на середовищі, і роль на стеку мають `EnvironmentId`. Обидві мапляться в одну колонку через `HasColumnName`, а унікальний індекс «користувач + середовище» відфільтровано за дискримінатором.
5. **`DbContext` у довгому gRPC-виклику.** З'єднання агента живе годинами; один `DbContext` на весь виклик тримав би застарілі сутності. Кожна операція з БД виконується в окремому DI-scope.
6. **Назви без урахування регістру.** Унікальність назв середовищ, репозиторіїв і користувачів — через колацію `NOCASE`, а не нормалізацію рядків у коді.
7. **Інструмент міграцій.** `dotnet-ef` поставлено локальним інструментом (`dotnet-tools.json`), щоб у всіх була однакова версія; `IDesignTimeDbContextFactory` дає створювати міграції без запуску ЦА.

### Плюси й мінуси

_Дописати автору._

Факти: мапінг доменних класів без окремих моделей зекономив багато коду; частина обмежень SQLite проявляється лише під час виконання, а не компіляції; згенерований SQL видно в логах, але за замовчуванням його забагато (рівень логування для `Database.Command` знижено до Warning).
