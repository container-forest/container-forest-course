# Ретроспектива: ASP.NET Core Identity

- Пакет: `Microsoft.AspNetCore.Identity.EntityFrameworkCore` (і транзитивно `Microsoft.Extensions.Identity.Core` / `Stores`)
- Чи зараховується в лабу 3, ще треба з'ясувати: це пакет від Microsoft (див. «Вимоги курсу» в `CLAUDE.md`).

Кожен учасник, що працював із бібліотекою, пише свій розділ за питаннями з умови лаби 3.

## Денисенко Л. В.

### Які задачі розв'язує бібліотека

- Зберігання облікових записів для входу: хеш пароля (PBKDF2), лічильник невдалих спроб і блокування, security stamp. Доменний `User` про паролі не знає; `AccountUser : IdentityUser<Guid>` має той самий id.
- Вхід і сесія: `SignInManager` перевіряє пароль з lockout і видає cookie `cf_session`; `RememberMe` робить її постійною.
- Завершення сесій: після зміни пароля security stamp змінюється, і старі cookie перестають проходити перевірку.

### Чому саме ця бібліотека

Власну реалізацію логіну команда відкинула (`CLAUDE.md`, «Відкинуті альтернативи»): хешування паролів і сесії мають бути готовими й перевіреними. Альтернативи:

- окремий провайдер ідентичності (Keycloak, Authentik) — ще один сервіс у розгортанні, а проєкт розрахований на невеликі інсталяції;
- OpenIddict — сервер OAuth2/OIDC, потрібний, коли ми самі видаємо токени іншим застосункам; нам потрібна лише cookie-сесія для панелі;
- готові ендпоінти `MapIdentityApi` з ASP.NET Core 8+ — фіксований контракт і bearer-токени, а нам потрібні власні DTO й cookie `SameSite=Strict`.

ASP.NET Identity дає перевірене хешування паролів, lockout і security stamp і при цьому дозволяє тримати власні ендпоінти й доменного користувача окремо від облікового запису.

### Проблеми, що виникли

- `IdentityUserContext` має власну властивість `Users` (облікові записи), а в `AggregatorDbContext` була `DbSet<User> Users` (доменні користувачі). Приховування члена — попередження, а з `CI=true` — помилка збірки. Нашу властивість прибрали: її ніхто не використовував, таблицю задає `ToTable("Users")`.
- Зовнішній ключ `AspNetUsers.Id` → `Users.Id` не вдалося налаштувати: EF не з'єднує `Guid` з `UserId` (типізований id з конвертером). Обліковий запис і доменний користувач створюються в одному `SaveChanges` (`UserManager.CreateAsync` сам зберігає контекст).
- Перевірка security stamp за замовчуванням раз на 30 хв: зміна пароля не завершувала б інші сесії одразу. Поставили `ValidationInterval = 0`; ціна — запит до БД і нова cookie на кожну відповідь.
- `SignInManager` для невідомого імені відповідає швидше, ніж для неправильного пароля (хеш не рахується), і цим видає наявні імена. Додали перевірку пароля проти фіктивного хешу.
- Cookie-схема за замовчуванням перенаправляє на `/Account/Login`; для API перевизначили `OnRedirectToLogin` і `OnRedirectToAccessDenied` на 401 і 403.
- `UserManager.SetUserNameAsync` разом з ім'ям міняє security stamp, тож перейменування розлогінювало б користувача. Ім'я змінюємо напряму й зберігаємо через `UpdateAsync`, який сам оновлює нормалізоване ім'я.
- Готового «встановити пароль від адміністратора» без токенів скидання немає: `RemovePasswordAsync` + `AddPasswordAsync` — два збереження, і невдалий новий пароль лишив би обліковий запис без пароля. Перевіряємо пароль усіма `PasswordValidators`, потім міняємо хеш і security stamp одним збереженням.
- Власні правила паролів (`IPasswordValidator<TUser>`, `AddPasswordValidator`) Identity запускає всі й збирає помилки разом — зручно для форми з кількома причинами. Але ознаки «це помилка пароля» в `IdentityResult` немає: її розпізнаємо за префіксом коду `Password`, тож власні правила мусять дотримуватися того самого префікса.
- `UserManager` сам зберігає контекст після кожної зміни, тож доменні зміни, зроблені до виклику, зберігаються разом з обліковим записом. Це зручно для атомарності, але порт `IAccountStore` мусить прямо про це казати.

### Документація

Огляд Identity в документації ASP.NET Core орієнтований на застосунки з Razor-сторінками й готовим UI, а для API-only сценарію (cookie без редиректів на `/Account/Login`, власні ендпоінти) потрібні шматки з кількох сторінок. Неочевидні побічні ефекти (`SetUserNameAsync` міняє security stamp, `UserManager` сам зберігає контекст, інтервал перевірки stamp 30 хвилин) документація згадує в довіднику API або не згадує зовсім; їх виявили тести.

### Плюси й мінуси

Плюси:

- хешування паролів, lockout і security stamp готові й перевірені, власну криптографію писати не довелося;
- правила паролів додаються класами `IPasswordValidator`, і Identity сама збирає помилки всіх правил;
- таблиці облікових записів живуть у тій самій базі й тому самому `DbContext`.

Мінуси:

- побічні ефекти методів `UserManager` (збереження контексту, зміна stamp) не видно з їхніх назв;
- деякі прості задачі не мають готового рішення: пароль від адміністратора без токена скидання, ознака «це помилка пароля» в `IdentityResult`;
- налаштування за замовчуванням розраховані на MVC: редиректи замість 401/403, перевірка stamp раз на 30 хвилин, різний час відповіді для невідомого імені.

### Що змінили б

Так само: Identity лише для облікових записів, а доменний користувач і права — окремо. Інакше: на початку написати тести на поведінку, яка важлива для безпеки (час відповіді для невідомого імені, завершення сесій після зміни пароля, перейменування), і лише потім код: майже всі проблеми вище знайшли саме такі тести.
