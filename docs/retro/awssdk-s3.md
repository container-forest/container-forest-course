# Ретроспектива: AWSSDK.S3

- Пакет: `AWSSDK.S3` 4.0 (залежить від `AWSSDK.Core`), ліцензія Apache-2.0

Кожен учасник, що працював із бібліотекою, пише свій розділ за питаннями з умови лаби 3.

## Петренко Б. О.

### Які задачі розв'язує бібліотека

Завантаження зашифрованого архіву бекапу ЦА в S3-сумісний бакет (ADR-0014): Cloudflare R2, MinIO, RustFS чи AWS. Бібліотека будує запит, підписує його SigV4 і розбирає XML-помилки сервера. Використовується лише одна операція, `PutObjectAsync`, в одному класі `S3BackupStorage`.

### Чому саме ця бібліотека

S3-протокол — спільна мова всіх таких сховищ, а офіційний SDK — його найпоширеніша реалізація для .NET. Власний підпис SigV4 на `HttpClient` зайняв би небагато рядків, але це криптографічний код, який довелося б тестувати й підтримувати самим заради задачі, що не є суттю проєкту. Клієнт `Minio` для .NET ми не пробували: він здався менш поширеним, а вибір SDK не прив'язує нас до AWS, бо адреса сервера задається налаштуванням.

### Документація

Посібник AWS написаний про сервіси AWS: про сумісні сервери там майже нічого. Те, що для нас найважливіше, знайшлося не там, а в прикладі Cloudflare для R2. Той приклад написаний для версії 3 пакета, тож для версії 4 налаштування довелося звіряти окремо.

### Проблеми та як їх розв'язали

1. **Потокове підписування й R2.** Через HTTPS SDK типово надсилає файл частинами зі Streaming SigV4, а R2, за документацією Cloudflare, цього не підтримує. Перша реалізація пройшла всі тести й наскрізну перевірку на RustFS, бо вони йшли через HTTP, де SDK поводиться інакше. Помилку знайшли лише під час читання прикладу Cloudflare для цієї ретроспективи. Тест із локальним TLS-сервером її відтворив, виправлення — `UseChunkEncoding = false`: звичайний запит із підписаним хешем файлу, який розуміють усі сервери. Cloudflare радить `DisablePayloadSigning`, але тоді вміст не входив би в підпис.
2. **Контрольні суми за замовчуванням.** Нові версії SDK додають власні контрольні суми, які не всі сумісні сервери знають. На клієнті стоять `RequestChecksumCalculation` і `ResponseChecksumValidation` зі значенням `WHEN_REQUIRED`, а тест через HTTPS перевіряє, що заголовків контрольних сум у запиті немає.
3. **Сумісні сервери.** Потрібні `ServiceURL`, `ForcePathStyle` (бакет у шляху не вимагає DNS для нього) і `AuthenticationRegion`, бо `auto` з R2 не є регіоном AWS.
4. **Тести без сервісу.** SDK не абстрагований, тому тести запускають маленький локальний сервер на `TcpListener` (за потреби з TLS і `HttpClientFactory`, що приймає його сертифікат) і перевіряють сирий запит: метод, шлях, підпис, вміст.
5. **Зрозумілі помилки.** Відмова сервера — `AmazonServiceException`, з якого адміністратор бачить `ErrorCode` (`AccessDenied`, `SignatureDoesNotMatch`). Мережеві збої — `AmazonClientException` або `HttpRequestException`. Обидва випадки стають текстом у панелі без жодного секрету.
6. **Сервер для наскрізної перевірки.** Образи MinIO більше не завантажуються анонімно, тож перевіряли на RustFS, який теж перевіряє підписи.

### Плюси й мінуси

Плюси:

- підпис і розбір помилок готові, а `ErrorCode` одразу придатний для показу людині;
- працює з будь-яким S3-сумісним сервером через налаштування;
- не треба власного криптографічного коду.

Мінуси:

- близько 2,2 МБ збірок (`AWSSDK.S3`, `AWSSDK.Core`) заради однієї операції;
- типові налаштування розраховані на AWS: потокове підписування й контрольні суми доводиться вимикати для сумісних серверів, а помилка видна лише на конкретному сервері й лише через HTTPS;
- клієнт не підміняється простим способом, тому тестувати доводиться на рівні HTTP.

### Що змінили б

Від початку перевіряли б через HTTPS на тому сервері, куди справді підемо: тест на іншому сервері через HTTP дав хибну впевненість. Перед написанням коду читали б приклад саме для нашого сховища, а не лише посібник SDK. На момент написання завантаження на справжній R2 ще не перевірялося, це перший крок після деплою.
